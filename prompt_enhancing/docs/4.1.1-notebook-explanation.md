# Understanding the 4.1.1 Complete Pipeline Notebook

## Overview

The `4.1.1-complete_pipeline.ipynb` notebook is a comprehensive implementation of an archaeological data extraction pipeline that processes PDF documents containing archaeological intervention reports and extracts structured metadata using Large Language Models (LLMs). This notebook represents a complete end-to-end workflow for transforming unstructured archaeological documents into structured, analyzable data.

## What the Notebook Does

### 1. **Complete Archaeological Data Extraction Pipeline**

The notebook implements a machine learning pipeline that:

- **Processes PDF Documents**: Takes archaeological intervention reports in PDF format
- **Extracts Text Content**: Uses OCR and text extraction techniques to convert PDFs to processable text
- **Applies NLP Processing**: Uses Named Entity Recognition (NER) and other NLP techniques to identify relevant information
- **Structured Data Extraction**: Employs LLMs to extract specific archaeological metadata fields
- **Validates and Evaluates**: Scores the extraction accuracy against ground truth data

#### **Main Extractors Implemented**
- **Intervention Date Extractor**: Identifies start and end dates of archaeological interventions

## How to Read the Results

### 1. **Evaluation Metrics**

The notebook produces several types of results:

#### **Per-Field Scores**
```python
per_field_scores, detailed_results = infering.score_dag(trained_dag_parts, eval_inputs, ds)
```

This returns:
- **Accuracy scores** for each extracted field (0.0 to 1.0)
- **Field-specific performance** showing which types of information are extracted most reliably

#### **Detailed Results DataFrame**
The `detailed_results` contains:
- `id`: Document identifier
- `field_name`: Name of the extracted field
- `predicted_value`: What the model extracted
- `expected_value`: Ground truth value
- `evaluation_method`: How the prediction was scored
- `metric_value`: Numerical score for this prediction

### 2. **Understanding the Output Tables**

When you see results like:
```
✔️ [0.500]  # Correct extraction with 50% confidence
❌ [0.000]  # Failed extraction
✔️ [0.950]  # High-confidence correct extraction
```

This indicates:
- **✔️**: Successful extraction matching ground truth
- **❌**: Failed or incorrect extraction
- **[0.XXX]**: Confidence score or accuracy metric

### 3. **Visualization Components**

### 4. **MLFlow Integration**

Results are tracked in MLFlow with:
- **Experiment runs** with hyperparameters

## Interpreting Specific Results

### **Date Extraction Results**

Example output:
```
intervention_start_date_min: 1987-09-27
intervention_start_date_max: 1987-09-27  
intervention_start_date_precision: "day"
```

This means:
- The intervention started on September 27, 1987
- Start and end dates are the same (single-day intervention)
- Precision is at the day level (not just month/year)

### **Location Extraction Results**

Example output:
```
university.Comune: "Roma"
university.Sigla: "RM"  
```

This indicates:
- Municipality: Rome
- Province code: RM (Rome)
- Confidence in extraction can be seen in associated metrics

### **Performance Interpretation**

- **Scores above 0.8**: Excellent extraction quality
- **Scores 0.6-0.8**: Good quality, may need review
- **Scores below 0.6**: Poor quality, likely needs manual verification
- **Missing values (NaN)**: Information not found in document

## Troubleshooting

### **Common Issues**

1. **LLM Context Overflow**: Handled by `_focus_and_truncate()`
2. **Date Parsing Errors**: Handled by `_predict_safe()`
3. **Missing Ground Truth**: Results in NaN values in evaluation
4. **Network Timeouts**: May require retrying LLM calls

### **Performance Optimization**

- **Batch Processing**: Process multiple documents together
- **Caching**: Reuse OCR and NER results
- **Prompt Optimization**: Use DSPy's automatic optimization
- **Model Selection**: Choose appropriate LLM size for speed/accuracy trade-off
